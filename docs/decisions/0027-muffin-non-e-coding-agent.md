# ADR-0027 — Muffin non è un coding agent: legge ed esegue, non sviluppa

**Contesto.** ADR-0015 dava alla capability `dev` due livelli: (a) lavori piccoli col proprio loop su un clone dedicato → branch+PR; (b) lavori grossi orchestrando un harness di coding maturo via API. In M3 ho costruito il livello (a) — `dev_clone` + `dev_run` su workspace sotto `~/.muffin/dev/` (commit `7d2d175`). Direttiva owner (2026-08-09, dopo due redirect consecutivi sulla stessa area — quindi trattata come tronco, non ritocco): *"Muffin non è un coding agent, al massimo farà script da runnare ma non farà effettivo coding… i check che fanno i comandi dev possiamo farli in generale nel comando bash."* Il livello (a) fa competere Muffin con harness di coding maturi (Claude Code, Cursor) — esattamente il "non riscrivere roba risolta" dei principi, e fuori dall'identità del progetto (specchio + agente che orchestra, non strumento di coding).

**Decisione.** Il livello (a) è **tagliato**. Muffin, sul codice, fa tre cose e nessuna di più:
1. **Legge** — `fs_read`/`fs_list` nella working directory, per capire come funziona un codebase e cosa fare.
2. **Esegue script contenuti** — `shell_run` nel sandbox: write-scope alla project dir + TMPDIR di sessione, niente rete, timeout, output troncato. È l'**unico tool comando**: i controlli che stavano nei comandi dev vivono qui, in generale, non in una superficie "dev" separata. C'è un solo modo di eseguire un comando e si contiene una volta sola.
3. **(tetto, differito) Orchestra** un coding agent esterno via API (ADR-0015 livello b) per il lavoro di sviluppo vero. Non lo si reimplementa; quando servirà, Muffin scrive il brief e fa da committente. Non entra in v1.

L'**introspezione effettiva** (leggere i propri trace, referti su di sé) resta un differenziale desiderato ma è **M6** per costruzione — lì si progetta con gli span citati, non a metà adesso.

**Alternative scartate.** *Tenere il livello (a)* (clone+branch+PR fatti da Muffin): rende Muffin un coding agent mediocre in un campo con investimenti fuori scala, e sottrae energie al differenziale (memoria/introspezione). *Un tool `dev_run` separato accanto a `shell_run`*: due tool che prendono entrambi una stringa `command` sono il sedimento che il rebuild combatte — il meccanismo è uno (`executor.run`), la superficie deve esserlo. *Una capability `dev` a rischio ridotto per il clone usa-e-getta*: senza il clone non serve; il gradiente di blast-radius che la giustificava è sparito col livello (a).

**Conseguenze.** Più facile: M3 si semplifica (un solo primitivo d'esecuzione, un solo punto di contenimento); l'identità resta pulita (Muffin non promette coding che non fa). Più difficile: "Muffin costruisce Muffin" diventa solo orchestrazione, e quella è differita — il bootstrap di auto-sviluppo non arriva in v1 (il primo passo resta "legge i propri trace", che è lettura, non sviluppo). Rimosso codice funzionante e testato (`core/dev/`, `agent/tools/dev.ts`, 11 test) — il costo di aver costruito nella direzione sbagliata prima del redirect, pagato subito invece di sedimentare.

**Reversibilità.** Alta. Il livello (b) è dietro API e resta la strada dichiarata per il coding vero quando lo si vorrà; ri-aprirlo non tocca nulla di ciò che resta. Segnale che questo taglio era sbagliato: l'owner si ritrova a chiedere ripetutamente a Muffin di fare modifiche di codice end-to-end che l'orchestrazione esterna non copre — ma allora la risposta è cablare il livello (b), non resuscitare il (a).
