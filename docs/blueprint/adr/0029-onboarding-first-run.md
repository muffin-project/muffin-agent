# ADR-0029 — Onboarding e first-run: prompt interattivo, inferenza provider, install→init

**Contesto.** `muffin init`, se mancava la API key, falliva con exit 1 stampando "missing — set MUFFIN_API_KEY", senza chiederla: un onboarding per esperti, non "da 0 a prima conversazione". Il docstring di `cli/init.ts:25` prometteva già *"interactive prompts only when stdin is a TTY"*, ma il prompt non era mai stato scritto — gap dichiarazione-vs-codice (`PRACTICES.md §5`, "il meccanismo dichiarato ≠ quello che il codice fa"). Prior art su fonte primaria (`research/onboarding-first-run.md`, scout 2026-08-09): sui 6 CLI studiati lo split sul prompt del segreto è **3 vs 3** — Goose (`cliclack::password().mask`), gh (`survey.Password`), Hermes (raw-termios + fallback getpass) hanno un vero prompt mascherato; Claude Code, aider, Ollama no (solo OAuth-browser o env). Tensione documentata (gh #10922): "mai un flag, solo stdin" è sicuro ma confonde chi vuole incollare. Anti-pattern più solido (Hermes, nel loro stesso codice, `setup.py:398`): un wizard può "completare con successo" senza un provider funzionante se nessuno step finale lo controlla.

**Decisione.**

1. **Su TTY, se la chiave manca, `init` la chiede** — input nascosto, no echo (`cli/prompt.ts`), preceduto da un hint "prendi la chiave qui". Headless resta l'errore-che-nomina-il-flag: nessun prompt blocca una pipe. Colma il gap docstring-vs-codice. Siamo nel gruppo CLI-native (Goose/gh/Hermes), non in quello OAuth-browser.
2. **Il provider si inferisce dalla forma della chiave** — `sk-or-`→openai-compat + base-url OpenRouter, `sk-ant-`→anthropic diretto. È la risposta a "quale provider" **senza una lista**, coerente col principio operativo (inferisci, non chiedere liste). `--provider` esplicito vince sempre; prefisso ignoto → default del chiamante.
3. **`muffin` nudo senza config → first-run**: chiede "setup adesso? [Y/n]" (pattern Hermes B), non lancio silenzioso alla Claude Code né errore secco alla gh. Off-TTY stampa il comando, non si appende.
4. **`install.sh` a fine, su TTY, offre `muffin init`** (Goose/Hermes incatenano il wizard). Off-TTY stampa i prossimi passi.
5. **Nessuna validazione della chiave a init.** Claude Code non valida → #28176 ("accettata al login, fallisce al primo messaggio"). La verifica live sta in `muffin doctor --online`, che già esiste. `init` resta onesto: segna `!` gli step incompleti ed esce 1, mai un falso successo (anti-pattern Hermes #7).

**Alternative scartate.** *Menu provider stile Goose/Hermes*: una lista esplicita, contro "inferisci, non chiedere"; l'inferenza da prefisso copre i due casi reali a costo di zero domande. *OAuth-browser stile aider/Claude Code*: rotto proprio negli ambienti che ci interessano (SSH/headless/container — Claude Code #66332/#48048), e lega a un flusso per-provider; il prompt incollabile è portabile e provider-agnostico. *Validare la chiave a init*: latenza + dipendenza di rete nel primo comando, delegata a `doctor --online`.

**Conseguenze.** Più facile: "da 0 a prima conversazione" in un gesto (install → offre init → init chiede la chiave con l'hint giusto → doctor). L'inferenza fa funzionare la chiave OpenRouter dell'owner senza flag, e aiuta anche gli script (`MUFFIN_API_KEY=sk-or-… muffin init`). Più difficile: il prompt nascosto è codice terminale (readline con echo soppresso) — mitigato lasciando a readline la line-discipline (backspace, sequenze di escape assorbite) e **testando la lettura con un TTY finto** (i prompt sono iniettabili; +read-test oltre al fallback non-TTY). Da tenere d'occhio: un provider nuovo con un prefisso-chiave nuovo va aggiunto a `inferProvider`.
