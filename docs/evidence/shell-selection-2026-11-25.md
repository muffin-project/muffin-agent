# Shell selection on the first consent

Two real-inference turns selected `shell_run` for a command that had to write a project file. The second turn exposed both shell tools. The first consumed one approval and sandbox enforcement denied the write. In the second, the fixture withheld consent to the wrong scope. See [#1018](https://github.com/muffin-project/muffin-agent/issues/1018) and the [runtime evidence](https://github.com/muffin-project/muffin-agent/pull/1017#issuecomment-7147723614).

The runtime checks a static capability before it runs each handler. Read-only commands can write only to scratch. The separate workspace-write capability is evaluated against the same authority and is bound to the exact invocation by #1017. Both scopes currently require approval.

| Candidate | Supporting evidence | Evidence against it or falsifier |
| --- | --- | --- |
| Retain the two model tools and front-load the difference | Smallest change. The OpenAI function guide recommends concrete examples for recurring mistakes. | The first trial did not reach either shell. Shortening descriptions also changed lexical discovery, so the live run cannot distinguish model choice from discovery. |
| Expose one command schema with a required effect | The OpenAI Shell and Anthropic Bash APIs document a single command interface. OpenClaw documents one exec interface and separately evaluates host policy. | The model can still choose the wrong effect. Incorrect or missing effects must reach neither shell. The adapter must preserve the exact pending call and the result across a gateway restart. |
| Remove the model's choice and infer scope from command syntax | Frees the model from assigning an effect. | A general command or invoked program can do work the surrounding syntax does not describe. Automatically assigning greater scope would change the consent and authority model. |

Prototype the single schema on the local baseline composition `f810924c`. Route a valid declaration to the existing capability before checkpoint and policy. This isolates the model-interface comparison. It makes no change to discovery, the sandbox or consent rules. Test the original file task and an independent stdout-only task. Reject the design if it increases approvals for a read, crosses scope, loses a durable outcome, or fails to improve the first choice with real inference.

The first prototype showed the new menu only when both scopes were visible. After a restart, the existing recovery restores the approved tool without requiring the related tool. The compiled fixture obtained the expected bytes and receipt but failed its resumed menu assertion. The next prototype keeps the same interface when one scope is visible and only lists that scope in the input schema. Declarations of other scopes do not reach the native capability dispatch.

On local `5cacdff2`, both compiled native gateway fixtures passed after restart. The write scope produced the file and a single recorded result. The read scope returned the line count and left the input unchanged. Both used one approval. Four focused tests cover the mapping, unavailable and missing effects, a reserved-name collision and the provider-facing history.

The live-model write used the pinned free Nemotron route, synthetic input and loopback Telegram. It selected `shell` and requested the correct write capability on the first consent. Muffin wrote the expected `29`, consumed one approval and recorded one successful write. The Telegram edit delivering the number matched the durable message ID. Four HTTP 200 requests, 149 seconds total and zero reported cost with embeddings off. The first automated receipt assertion was too strict about the stored HTML. The Bot API edit and the delivery record independently establish the result. The same edit falsely called the successful command interrupted, reproduced separately in #1019.

In the held-out real-model read, the model named the legacy read tool before discovery. It ran once under read-only scope, consumed one approval and did not create an output file. The final reply did not arrive within the test budget and the trace includes an upstream 502. This is evidence for the read execution only. Keep the prototype local until its behavior is checked on the integrated base and the read journey is fully confirmed.
